## 二、已修复项

### D-1 密码学重活占用主线程（M2 自查发现，非评审项）

- **现象**：`VaultViewModel` 在 `viewModelScope`（`Dispatchers.Main.immediate`）内调用认证用例与条目仓库，而 Argon2id 派生（64MiB/3 轮）与 SQLCipher 开库均为阻塞重活 → 解锁过程掉帧乃至 ANR。
- **修复**：调度器下沉到数据层，用例与仓库内部 `withContext`：
  - 认证用例（`InitializeVault`/`UnlockVault`/`ResetVault`/`ChangeMasterPassword`/`ChangeSecurityQuestions`/`BiometricToggle`）注入 `computeDispatcher`，默认 `Dispatchers.Default`；
  - `EntryRepositoryImpl` 注入 `ioDispatcher`，默认 `Dispatchers.IO`，`search` 另加 `flowOn`。
- **验证**：`UnlockVaultTest.kdf runs on the injected dispatcher rather than the caller thread`（注入记录型 dispatcher，断言确被用于调度）。
- **影响**：调度器默认值使 DI 接线与既有调用点无需改动；测试可注入测试调度器。

### G-A 认证限流非原子

- **现象**：解锁按钮连点会并发启动多个解锁协程，各自读到同一 `failedAttempts` 再各自写回 → 失败计数丢失，BR-9（5 次锁 1 分钟）被削弱；同时并发 Argon2 派生叠加内存（呼应 G-G 的 OOM 风险）。
- **修复**：`AuthThrottle.serialized { }` 提供进程内互斥临界区，六个认证用例的「读 Header → 锁定检查 → 校验 → 计数+1 → 写回」整段串行化，用例签名相应改为 `suspend`。
- **验证**：`UnlockVaultTest.concurrent failures are all counted without lost updates`。该测试经反向验证——临时旁路互斥即失败，确认具备回归捕获能力。
- **代价**：第二次尝试需等待第一次完成。相对「锁定被绕过」，可接受。

### G-F 密保校验重复实现

- **修复**：提取 `SecurityQuestionPolicy`（3 道 / 问题 ≤100 / 答案 ≤60，Trim 后计），`InitializeVault` 与 `ChangeSecurityQuestions` 共用。
- **验证**：`VaultMaintenanceTest.change security questions rejects overlong question like initialization does`（并断言校验失败不改写 Header）、`...rejects wrong question count`。

### G-G（部分）限流参数误配

- **修复**：`AuthThrottle` 构造期 `require(maxAttempts > 0)` / `require(lockDurationMs > 0)`，避免 `maxAttempts=0` 之类误配让 BR-9 静默失效。

### L-1 备份/迁移策略

- **修复**：新增 `app/src/main/res/xml/data_extraction_rules.xml`，在 Android 12+ 显式关闭云备份与设备间直传（`allowBackup="false"` 在 12+ 仅约束云备份，不覆盖 D2D）。两者并存：前者管 12+，后者管 11 及以下。

## 三、已记录但推迟

### G-C 限流时钟的 wall-clock 回拨窗口

- **问题**：`lockUntilEpochMs` 取自 `System.currentTimeMillis()`，用户把系统时间调早可缩短锁定窗口。
- **推迟理由**：修复需在 Header 增补持久字段（`lockSetAtElapsedMs`），而 Header 覆盖 HMAC 覆盖全字段——新增字段会改变 MAC 输入，令既有库一律校验失败。收益相对有限（需物理接触 + 每次尝试 Argon2 约秒级），当前形态为「纵深不足」而非可绕过。
- **计划**：T29 硬化时随 Keystore 托管升级一并评估，届时可同时处理 Header 格式升级（一次性迁移 + 一次性重包裹）。
- **当前缓解**：Argon2 参数 64MiB/3 轮使每次尝试成本高，叠加 G-A 的并发串行，暴力尝试的实际吞吐进一步下降。

### G-G（剩余）Argon2 参数标定

- **推迟理由**：标定需在目标机型上测得「单次派生耗时」与「峰值内存」，模拟器/开发机数据不能代表低配真机。
- **计划**：T29 硬化时在 2–3 档真实配置上实测，确认 `KdfParams(3, 65536, 4)` 在低端机上的 P95 耗时与内存占用；必要时提供「高强度/兼容性」档位。

## 四、已决策并落地（2026-09-24 用户拍板）

三项原为「待产品决策」，用户均选择推荐方案，已在 M2 收尾中实现。

### G-B Header 损坏 → 「清除重建」入口 ✅

- **决策**：提示数据不可用 + 提供「重置密码库」入口，**两级确认**并明示数据永久丢失。
- **实现**：
  - 数据层：新增 `DestroyVault`（删除 Body 库与 Header，幂等）、`VaultHeaderStore.delete()`、
    `VaultDatabaseProvider.delete()`（先关连接再删文件，避免 SQLCipher `-wal`/`-shm` 残留）；
  - 状态层：`VaultUiState.vaultCorrupted`；`VaultViewModel` 在 `initialize`/`unlock` 捕获
    `HeaderIntegrityException` 置位（原先异常直接上抛 → 协程崩溃）；损坏时不进初始化流程
    （`VaultStatus` 已按「宁严勿松」处理），仅显示损坏态；
  - UI：`CorruptedVaultNotice`——第一级说明原因与「无云备份无法自动恢复」，第二级明示
    「永久删除且无法恢复，建议先从备份恢复」。
- **验证**：`DestroyVaultTest`（删净/幂等/可重新初始化）、`VaultViewModelTest`
  （损坏态上屏、清除后回到未初始化且锁定会话）。
- **设计约束**：`DestroyVault` 不接受「已确认」标记参数——确认责任放在 UI 分支，
  避免可被误传的布尔量把破坏性操作放行。

### G-D 生物识别 → `BIOMETRIC_STRONG` ✅

- **决策**：只接受 Class-3 强认证；仅有 2D 面容的设备失去生物识别快捷解锁，改用主密码。
- **实现**：`AndroidBiometricGate` 在 API 30+ 改用 `BIOMETRIC_STRONG`。
- **平台限制（无法弥补，如实记录）**：androidx 在 API 29 及以下**不能区分认证等级**，
  只能报告「是否有任意生物识别已录入」，故该段系统的纯 2D 面容设备仍会被判为可用。
  这是框架能力边界。兜底是 Keystore 侧 `AUTH_BIOMETRIC_STRONG` 密钥要求，API 30+ 会在
  加密层再次拒绝弱认证。

### G-E Keystore → auth-per-use ✅

- **决策**：每次解锁都需认证，且密钥操作与该次认证绑定。
- **实现**：
  - API 30+：`setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`（0 = 每次使用都需重新认证）；
    API 26–29 框架无「每次使用」API，等价语义为 validity = `-1`（仅生物识别，每次使用都需认证）。
  - `KeystoreDekVault.unwrap` 不再自行 init cipher，改为接收**已认证**的 cipher；
    新增 `createDecryptCipher()` 供 `BiometricPrompt` + `CryptoObject` 流程使用。
- **安全要点**：密钥仅在单次认证会话内可用，认证后无法另行使用——这正是相对
  30s 窗口的本质改进。
- **⚠️ 运行时验证缺口**：本机模拟器无已录入的 Class-3 生物特征，
  `KeystoreDekVaultTest` 的 3 个 auth 相关用例在 `assumeStrongBiometric()` 处**跳过**，
  仅 Keystore 基建冒烟用例真正执行。该行为目前**只有编译期与代码审查保证，未在设备上实测**，
  需在有指纹/3D 面容的真机上补跑一次（并连带验证 `BiometricPrompt` + `CryptoObject` 的 UI 接线，
  该接线本身属 M3 范围）。

### 顺带修正的测试基建缺陷

`KeystoreDekVaultTest` 原把 `assumeTrue` 放在 `@Before`，导致**所有**用例（含不依赖
生物识别的 Keystore 基建冒烟）在无生物特征设备上一并跳过——冒烟用例形同虚设。
已把跳过条件下沉到 3 个 auth 相关用例内部，冒烟用例恢复真实执行。
这也意味着此前报告中「platform androidTest 4 通过」实为 4 个全部跳过，特此更正。
