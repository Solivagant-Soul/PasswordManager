## 一、阻塞（Blocker）

### B1. 解锁引导元数据与 SQLCipher 加密库「循环依赖」

- **位置**：§4.1 数据模型、§4.2 加密模型、D2/D8
- **原因**：方案将 `saltKdf / kdfParams / wrappedDekMaster / failedAttempts / lockUntil / 密保问题文本` 放入 SQLCipher 加密的 `VaultRecord`/`SecurityQuestion`，而 SQLCipher 库密钥又等于 DEK（§4.2）。解锁路径形成死循环——**开库需 DEK，取 DEK 需开库读 `wrappedDekMaster`+盐**。此外 `failedAttempts/lockUntil`（限流）与密保**问题文本**（找回展示）都必须在开库前可读，当前也在加密库内。
- **建议**：抽出独立 **Vault Header**（不依赖 DEK 的存储），承载盐、KDF 参数、`wrappedDek*`、失败计数、锁定时钟、密保问题；并对可变字段加 **HMAC 完整性保护**，防止篡改绕过限流（BR-9）。
- **处置**：已在 v0.3 §4.1/§4.2 修正。

## 二、严重（Major）

### S1. 密保答案派生恢复密钥的编码/归一化未定义

- **位置**：§4.2 `密保答案组合 ──KDF──> KEK_recovery`
- **原因**：多答案拼接顺序、分隔/长度前缀、以及需求 §6.2 的「Trim + 大小写敏感」在派生前如何执行均未定义。后果：`["ab","c"]` 与 `["a","bc"]` 同密钥；或设置/找回归一化不一致 → **永久无法恢复数据**。
- **建议**：定义规范化编码（Trim → 固定顺序 → 长度前缀 + UTF-8 → 拼接 → KDF），两端一致。
- **处置**：已在 v0.3 §4.2 定义，并纳入 T10 验收。

### S2. 备份/CSV 导入缺「事务与原子性」

- **位置**：T27、T28（对照需求 S45/S46/S47）
- **原因**：需求要求「导入失败不污染现有数据」「导出中断不产生半文件」，但任务验收未定义「临时文件/事务 → 校验通过 → 原子提交」，全量备份导入的覆盖/合并策略也未定。
- **建议**：补原子导出（临时文件 + rename）、原子导入（校验通过后提交，失败回滚）、明确全量导入=整库替换（二次确认）。
- **处置**：已在 v0.3 T26/T27/T28 补充。

### S3. 自动填充与「解锁会话」的跨组件边界未建模

- **位置**：§2 核心原则、§3 `autofill`、§4.2「DEK 仅存内存、切后台清零」
- **原因**：`AutofillService` 与主 Activity 可能不同进程/上下文，填充发生时未必有已解锁会话；与「内存 DEK 单例会话」冲突，可能导致填充取不到凭据。
- **建议**：明确 autofill 的会话共享或内联解锁机制与 DEK 生命周期边界。
- **处置**：已在 v0.3 §3/§6 补说明，并纳入 T25 验收。

## 五、各维度结论速览

| 维度 | 结论 |
|---|---|
| 1 需求与验收覆盖 | 良好；改密保、锁定档位、排除易混淆、导入原子性等未映射到任务（已修） |
| 2 架构合理性 | 合理；1 处阻塞（Header 未分离）+ 1 处过度拆分风险 |
| 3 数据模型 | 分层清晰；Header/Body 未分离是硬伤（已修） |
| 4 API 设计 | 本地方案无 REST 要求；内部接口不完备、参数类型不一致（已修） |
| 5 安全/性能/并发/事务/幂等 | 安全重心正确；事务与导入原子性、限流计数完整性为重点缺口（已修） |
| 6 既有系统冲突 | 无冲突；与 openapi.yaml 的预留语义差异已标注 |
| 7 任务可执行性 | 粒度（30–120min）与依赖标注合格；个别依赖过串行（已调整） |
